# tpt-strata — v1.1 Scope Decisions

**Date:** 2026-09-12
**Source:** Phase 10 review findings (todo.md §Phase 10)

This file records the *deliberate* scope decisions from the post-1.0.1 review.
Each item below is a decision, not a bug: tpt-strata's v1.1 subset is
deliberately small, and everything outside it either (a) gets a **targeted
diagnostic** pointing here, or (b) is communicated here for a documented
reason. The go/no-go for each "maybe" item is demand-gated by its named
consumer.

## SQL features — deferred to a future release (targeted diagnostics today)

The SQL parser rejects each of these with a message naming the construct and
referencing this file. They were excluded from v1 because none of the three
known consumers' v1 query workloads require them (spec.txt §4 scope):

| Construct | Rejection hint today |
|---|---|
| `OR` in `WHERE` | combine predicates with `AND` only |
| Parentheses / operator precedence in `WHERE` | combine predicates with `AND` only |
| `IS NULL` / `IS NOT NULL` | filter on a sentinel value instead |
| `IN (...)` | use a chain of `=` predicates with `AND` |
| `BETWEEN` | use `col >= low AND col <= high` |
| `LIKE` | use an exact `=` comparison |
| `DISTINCT` | use `GROUP BY`, or deduplicate in the caller |
| `HAVING` | filter aggregated results in the caller, or nest two queries |
| `LEFT` / `OUTER` joins | only a single inner equi-join is supported |
| Multiple `JOIN`s per query | only a single equi-join is supported |
| Column-to-column comparisons in `WHERE` | compare a column against a literal |

Every one is easy to express in the supported subset today. Revisit when a
consumer sends a real query that needs one — at that point it graduates to a
normal feature (parser + binder + engine + test), not an accident.

## Data types — evaluated, deferred pending consumer confirmation

| Type | Decision | Why |
|---|---|---|
| `Date` / `Timestamp` | **Deferred** | Highest Parquet-relevant gap; load-bearing decision. Confirm tpt-cloud-observability's actual schema needs first — adding `Date`/`Timestamp` touches `Scalar`, `DataType`, every array, engine comparisons, `format.rs` inference, and the Parquet bridge, so it should be driven by a real column, not a guess. |
| `Decimal` | **Deferred** | Same blast radius as `Date`; no consumer has asked yet. |
| `Int8` / `Int16`, unsigned ints, `Float32`, `Binary` | **Lower priority** | Narrow real-world use; revisit in the same pass as `Date`/`Decimal`. |

Adding a type is a deliberate, cross-cutting change — the honest cost is
"touches the whole native format", so each should be bought by a concrete
consumer need.

## Forward-looking ideas — demand-gated

| Idea | Gate |
|---|---|
| `Table::from_rows` row-oriented convenience constructor | Add when a consumer shows row-building is awkward; `Column::new` + `Scalar` covers v1. |
| `EXPLAIN`-style plan printing | Build on the diagnostics infra when a consumer debugs a plan. |
| Streaming / incremental aggregation mode | tpt-cloud-observability (a named consumer) is the demand signal; specify the windowed semantics with them before building. |

## Memory model commitment (applies to all of the above)

`Sort` and `Join` fully materialize their inputs in memory today — neither
operator streams or spills. Any feature above that assumes bounded-memory
`ORDER BY`/`JOIN` must come with a spec change, not a silent assumption
(see ARCHITECTURE.md §Execution characteristics).
